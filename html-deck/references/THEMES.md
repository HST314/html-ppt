# THEMES

所有主题只定义 token，不改变 DOM 结构。Agent 不得自由书写 hex；需要品牌适配时，把品牌倾向映射到最接近的 token。

## business-dark

客户汇报、销售成果、产品路线图默认主题。深背景、清晰高亮、适合大屏。

## business-light

正式报告、打印和白底会议屏。高对比黑白灰，配一个稳重强调色。

## tech-dark

技术分享、系统架构、数据平台。深色控制台感，但保留商务可读性。

## editorial

趋势洞察、行业观点、品牌故事。强调标题排版和图片叙事。

## warm-human

培训、组织沟通、客户成功案例。更温和的底色与人文照片友好。

## minimal-white

打印优先、法务/财务/高层审阅、信息密度高的文稿。结构克制，颜色少。

## token 约定

每个主题 CSS 必须提供：

- `--bg`、`--surface`、`--surface-2`
- `--text`、`--muted`、`--inverse`
- `--accent`、`--accent-2`、`--line`
- `--shadow`、`--radius`
- `--font-sans`、`--font-serif`、`--font-mono`
- `--slide-padding`、`--title-size`、`--body-size`

## 深色主题配色纪律

1. **背景色上限**:一套 deck 至多 1–2 种背景色;内容页共享同一 `--bg`,封面/尾页允许同色系加深变体,禁止每页换底。
2. **文字透明度阶梯**:深色底上的白色系文字只用 100%(正文)/ 72%(副题)/ 55%(说明)/ 45%(最弱可读档)四档,有效文字低于 45% 判 QA 失败(纯装饰水印除外)。
3. **accent 面反色文字**:accent(浅金/亮色)作为填充面时,其上文字必须使用 `--on-accent`(深墨,如 `#171106`),禁止白字压浅金(对比度仅约 2.4:1)。每个深色主题必须定义 `--on-accent`。
4. **token 派生,禁硬编码**:边框/阴影/光晕一律 `color-mix(in srgb, var(--accent) …)` 派生;主题文件内禁止出现与本主题无关的硬编码 hex/rgba(历史上 auto-derived 层残留异色边框/辉光即反面案例,必须清除)。
5. **双色分工**:accent = 强调与焦点(关键词、数据、焦点面);accent-2 = 结构与引导(编号、连接线、符号)。两色职责不交叉,禁止第三强调色。

## 色彩自动检测应与正文声明的色彩语言交叉核对

`detect_style.py` 的 `--accent` 来自场景图像素的真实色相/明度/饱和度分析，有图像依据，可信度较高；但 `--accent-2` 目前的推导方式是对 `--accent` 色相做一次固定的几何旋转（`hue+0.33`，即数学上「找一个和 accent 有区分度的第二色」），**不依据任何图像内容或文本内容，本质是猜测**，容易与 deck 正文实际描述的配色语言脱节。

**已实测踩坑案例**（`project-changzheng8a`）：deck.md 正文反复用「香槟金 / 18K 香槟金」描述全系列的强调色（边框、连线），但 `--accent-2` 经色相旋转落在 `#ff2f78`（品红），与文字宣称的色彩语言完全对不上——目录页卫星节点描边/编号、内容页的分组编号徽标、timeline 箭头、checkpoint 卡片描边等所有引用 `--accent-2` 的元素全部跟着显示成不搭调的品红色，读者观感是「这一块颜色像是贴上去的、和整体不是一套」。

**处置原则**：

1. **文本线索优先于几何猜测**——正文若高频、明确地点名了具体强调色名称（如反复出现「香槟金」「品牌红」「克莱因蓝」这类具名色彩描述，尤其是用来描述边框/线条/强调元素的场景），渲染时应当参考这类文字线索去校正/覆盖自动检测色，而不是完全信任没有语义依据的几何推导结果。
2. **只校正 `--accent-2`，不校正 `--accent`**——`--accent` 已经有图像像素分析作为依据，比合成的 `--accent-2` 可信得多，没必要用文本线索反过来动一个证据更强的值。
3. **触发要保守，避免误伤**——只在信号足够强（正文中相关色彩词出现次数达到一定阈值，且当前自动检测色与文字声明色的色相差异明显，比如超过 30°~40°）时才覆盖，偶发的一两次提及或色相已经比较接近的情况不触发，避免把「顺带提了一句某个颜色」误判成「这是全系列配色语言」。
4. **不追求覆盖所有色系的强 NLP 语义提取**——`scripts/detect_style.py` 当前只实现了「金色系」关键词表（`GOLD_KEYWORDS`）+ 香槟金锚点色的这一种最小可行实现（`--deck` 可选参数、`apply_text_color_override()`），可选传入 `deck.md` 路径触发；这不是一个通用色彩语义理解系统，只是一条防止「明显脱节」的保守校验。如果未来遇到其它明确具名色彩语言（如「藏青」「克莱因蓝」「胭脂红」）导致的类似脱节，优先按同样的最小实现模式扩展关键词表，而不是投入大量精力做成完全自动化的强 NLP 检测——这类色彩语义提取一旦做复杂，反而容易因为过度泛化而误伤本来没问题的项目；宁可保守只覆盖「有实测踩坑证据」的具体色系，也不要为了"看起来更智能"而引入不可靠的强判断。
5. **改动落点**：`scripts/detect_style.py --deck <deck.md>`（可选参数，未传时行为与此前完全一致，不影响其它项目）；具体实现见该文件 `GOLD_KEYWORDS`/`CHAMPAGNE_GOLD_HEX`/`apply_text_color_override()`。命中覆盖时会在 `state/style_report.json` 写入 `accent_2_text_override` 字段记录触发原因，便于事后追溯，未命中时该字段为 `null`。
