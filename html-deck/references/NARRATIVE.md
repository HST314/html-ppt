# NARRATIVE

本文件定义 `build_ir.py` 在生成 `outline.json` 时必须执行的叙事编排规则。目标是避免“每页几条要点”的薄 deck，让 Agent 先构建章节逻辑，再决定页面 role。

## 场景框架

### 客户汇报型（默认）

顺序固定为：背景与目标 → 关键成果（数据先行）→ 过程与方法 → 案例/证据 → 问题与应对 → 下一步计划 → 行动项。

成功判据：
- 每章至少 2 页内容页。
- 章间必须插入 `section` 过渡页。
- 默认页数 12-18 页；除非用户明确要求，禁止少于 8 页交付。
- 关键成果章节必须出现 `kpi` 或 `table`。

### 产品发布型

顺序固定为：痛点 → 洞察 → 方案 → 演示/截图证据 → 优势对比 → 路线图 → CTA。

成功判据：
- 痛点页必须是观点式标题，不得只写“用户痛点”。
- 演示/截图证据优先使用 `image-side` 或 `image-hero`，截图必须触发 `screenshot-frame`。
- 路线图必须使用 `timeline`，每个节点包含日期、事件、结果。

### 技术分享型

顺序固定为：问题 → 原理 → 架构 → 实现 → 数据验证 → 坑与经验 → 总结。

成功判据：
- 架构页优先 `two-column` 或 `image-side`。
- 数据验证页必须含目标对比、基准或实验口径。
- 坑与经验页必须包含“问题、原因、应对”三段式内容。

## 场景判断与故事线落盘

### 场景判断（总线第①步「项目理解」）

- `context/brief.md` 的 `scene_type` 必须映射到本文一类场景框架：`客户汇报` → 客户汇报型；`产品发布` → 产品发布型；`技术分享` → 技术分享型。
- 不在上列之内的场景（如培训教学）登记为「自定义场景」，并在 brief 中给出章节顺序理由（参照三类框架的成功判据格式书写）。
- 场景归类结论写入 `context/brief.md`，作为后续所有叙事判定的上游输入；缺归类结论按流程门禁判失败。

### 两层场景：deck 级 vs page 级（不得混淆或合并）

- 本文场景框架为 **deck 级场景**（客户汇报型 / 产品发布型 / 技术分享型 / 自定义），在总线①判定，决定全 deck 章节顺序、页数配额与叙事节奏。
- `references/design-scenario-system.md` 的 10 类为 **page 级场景**（封面/章节/品牌价值/产品介绍/项目方案/流程/数据/案例/成果展示/总结），在总线③逐页判定，决定单页版式选型倾向。
- 两层关系：deck 级场景决定各类 page 级场景的**配额与节奏倾向**（映射表见 design-scenario-system.md §0）；deck 场景不直接指定单页版式，page 场景不改变章节顺序。故事线落盘的「页数配额」即 deck 级场景对 page 级场景分布的约束出口。

### 故事线落盘（总线第②步「故事线分析」）

故事线分析结论逐章落盘到 `state/storyline.md`，机器可读表格，列序固定：

| 章节序 | 章节名 | 叙事任务 | 页数配额 | 节奏标注 |
| --- | --- | --- | --- | --- |

- 叙事任务：本章在故事线中承担的唯一职责（建立背景 / 数据先行 / 展示证据 / 解释机制 / 请求决策等）。
- 页数配额：本章内容页数量（不含 section 过渡页），受场景框架默认页数约束。
- 节奏标注：本章在全 deck 节奏中的位置（开场 / 推进 / 高潮 / 收束），收束段必须登记两页（行动页 + 结束页）。
- 表格之前须有一行场景框架登记（命中哪类场景框架或自定义场景）。
- 缺 `state/storyline.md` 或列字段空缺，按 SKILL.md 流程门禁判 QA 失败。

## 页面级硬规则

- 每套 deck 第 2 页必须是 `toc`。有 `##` 章节时目录使用章节名；没有章节时从内容页标题提炼 3—6 个叙事节点，不得省略目录。
- 收束必须占两页：倒数第 2 页是决策/行动页，承载负责人、时间与产物；最后 1 页才是 `closing`，只允许一个标题、至多一个短句和一个 CTA，不得放列表、表格、KPI、takeaway 或多图。
- 用户把大量内容标成 `closing` 时，必须将其改为倒数第 2 页的普通内容页，再另起低负载结束页；禁止通过缩小字体硬塞。

- `title` 必须是 action title：长度不少于 12 个非空字符，并包含数字或明确动词（提升、完成、验证、锁定、发布、交付、形成等）。
- 内容页至少 3 个内容块；不足时由 `build_ir.py` 自动补齐目标对比、过程证据、业务影响。
- `takeaway` 可选，默认不生成、不渲染（`build_ir.py` 不再自动截取导语或首条 bullet 拼一句
  "So-what：..."——那样做在结构上必然和页面正文同义复述，是"导语+列表+结尾句+takeaway"
  四重复读的根因之一）。只有当页面确有超出标题/导语的增量信息（新事实、新数字、新风险提示，
  而不是换个说法再讲一遍结论）时，才用 `<!-- takeaway: ... -->` 显式登记；写不出增量信息就不写，
  留空是正常状态，不是缺陷。`qa_render.py` 会检测显式登记的 takeaway 是否与导语/首条 bullet
  高度重复（字符重叠率阈值），命中即判反模式并扣分。
- 每页 `notes` 为 150-300 字口语化讲稿；先讲结论，再讲证据，最后给转场句。
- KPI 必须包含上下文：目标对比、同比/环比、行业基准或业务影响至少一种。
- 表格必须至少包含表头 + 4 行数据，最后一行作为合计或高亮结论行。
- timeline 每个节点必须包含日期 + 事件 + 结果，建议使用 `2026-03｜上线灰度｜投诉率下降 18%` 格式。

## Deck 级叙事门禁

按以下顺序检查，任一失败都要回到 IR 修复后重渲染：

1. 封面建立唯一主题，目录给出 3—6 个可追踪节点。
2. 中段每页只完成一个任务：提出判断、展示证据、解释机制或请求决策。
3. 所有输入图片在进入收束段前已展示；行动页之后不得追加证据图集。
4. 倒数第 2 页把前文压缩成可执行事项，最后一页只做情绪回收与单一 CTA。
5. 从封面、目录、章节页、行动页、尾页单独朗读时，仍能复述完整故事。

## 失败回退

- 输入标题不合格：IR 写入 `risk.issues`，QA 扣分；Agent 应优先改标题，不应只缩小字号。
- 内容块不足：`build_ir.py` 自动补齐结构化上下文，并在 `decision` 和 `risk` 中保留可审计痕迹。
- 页数不足：Agent 必须回到 Markdown 补充章节，而不是把一页塞满。
